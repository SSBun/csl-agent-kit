# Baseline Raw Output

## Arm D — 原始最终回复

结论：这个文件采用了紧凑的“目标注册表 + 通用执行器”设计，安装副作用也集中在少数函数中；主要问题不在结构复杂度，而在“安装完成”的判定与真实状态不一致。

### 执行结构

`main` 依次完成四件事：

```text
解析 install 参数
→ 决定目标集合
→ 顺序调用每个目标
→ 输出结果并设置退出码
```

`targets` 同时承担目标目录和策略表的角色，三个 handler 分别处理 Cursor 链接、Codex 插件迁移和 Pi 安装。`dryRun` 通过同一份 options 下传到文件与命令执行层，没有另建预览流程。

### 需要优先处理的问题

1. **未安装也可能返回成功**

   `installCodexPlugin` 与 `installPi` 在找不到相应 CLI 时返回 `skip`（第 227–248 行），没有抛错。`installTargets` 只要 handler 正常返回，就写入 `ok: true`（第 209–218 行）。最终 JSON 的 `ok`、进程退出码和 “integrations ready” 都只依据这个布尔值。

   结果是：用户明确要求安装某个集成，但依赖缺失时，自动化仍收到退出码 `0`。最小修复是把缺失必需 CLI 当作该 target 失败；若产品确实允许跳过，则结果模型至少要区分 `ready`、`skipped` 和 `failed`，不能让 `skip` 进入成功计数。

2. **Codex 更新过程可能留下半完成状态**

   第 231–240 行先执行六次删除，再添加 marketplace 和插件。后两步任一步失败，旧安装已经被移除，而且没有恢复逻辑。允许失败的删除也可能掩盖权限或 CLI 状态异常。

   建议先做完整前置检查；能够延后的旧别名清理放到新安装成功之后。无法原子化的步骤应在错误结果中保留已执行动作，让调用者知道系统处于部分变更状态。

3. **命令执行结果在展示层被压扁**

   `runCommands` 会保存 `status`，但允许失败的命令仍统一标记为 `action: "command"`（第 340–353 行）。摘要随后把所有 command 都描述为 “completed”，详细模式也没有输出 status（第 390–412 行）。

   这使诊断信息自相矛盾。无需引入新框架：仅在 change 中记录是否成功，并让摘要不要把非零状态称作完成即可。

4. **部分错误输入被静默接受**

   - `--all` 在显式 target 校验之前直接返回，因此 `--all --target invalid` 不会报告拼写错误（第 101–105 行）。
   - 未识别的顶层命令只打印帮助并正常退出，例如 `csl-agent-kit instal`（第 33–49 行）。

   两者都会削弱脚本调用的可检测性。显式 target 应始终校验；只有无参数或明确的 help 命令应成功显示帮助。

5. **几个较小的运行环境问题**

   - `process.env.CI` 只检查变量是否为真值，`CI=false` 也会禁止交互（第 110 行）。
   - 自动颜色模式没有检查 `process.stdout.isTTY`，管道输出可能携带 ANSI 控制码（第 416–418 行）。
   - `spawnSync` 没有 timeout，也没有优先报告 `result.error`；外部命令挂起或启动失败时，错误可读性较差（第 348–350 行）。

### 已有安全措施

- Cursor 目标不会覆盖普通文件或目录。
- 同一链接再次安装会返回 `unchanged`，具备幂等性。
- 旧 skill 清理只处理符号链接，并用 `isWithin` 限制来源范围。
- 选择记录通过临时文件后 rename，正式文件权限为 `0600`。
- `dry-run` 阻止实际命令、链接创建和链接删除。
- 单个 target 抛错后，其余 target 仍会继续执行并分别记录结果。

建议修复顺序：先纠正 `skip` 的退出语义，再降低 Codex 部分卸载风险，随后修复命令状态展示和参数校验。其余输出与环境细节可独立小改。

按要求仅进行了静态阅读，没有修改源码，也没有执行 CLI、构建或测试。

## Arm L — 原始最终回复

理解这个组件最省力的方法，是把它分成两台“小机器”：

```text
决策机器：用户想装什么？
执行机器：每个目标具体改变什么？
```

前半部分负责参数、交互和历史选择；后半部分负责符号链接、外部命令与结果展示。

### 第一台机器：选择目标

目标目录在第 9–31 行。每个条目包含：

- 用户可见的标题和说明；
- 是否由 `--yes` 默认选中；
- 是否会调用外部程序；
- 对应的安装函数。

当前目录的含义如下：

| target | 安装方式 | 默认选择 |
|---|---|---|
| `cursor` | 创建本地插件符号链接 | 否 |
| `codex-plugin` | 调用 Codex CLI 注册 marketplace 和插件 | 是 |
| `pi` | 调用 `pi install` | 否 |

参数解析位于第 51–99 行。目标既可以通过 `--target` 给出，也可以作为位置参数传入；逗号列表会拆分并过滤空值。

接着，第 101–155 行按照下面的顺序决定最终集合：

1. `--all`：全部目标；
2. 显式 target：校验、去重；
3. `--yes`：选择 `default: true` 的目标；
4. 都没有：进入交互多选。

只有第四条路径会读取历史选择并询问外部命令确认。非 TTY 或设置了 `CI` 时，不允许走交互路径。

### 第二台机器：执行目标

第 209–220 行的 `installTargets` 是统一调度器。它顺序调用每个 target 的 `run`：

- 正常返回：包装为 `{ target, ok: true, changes }`；
- 抛出异常：包装为 `{ target, ok: false, error }`；
- 一个目标失败不会终止后面的目标。

每个 handler 不直接负责打印，而是返回“发生了什么”的结构化记录。这些记录的 action 包括：

```text
symlink    创建或更新链接
unchanged  已经是期望状态
command    外部命令
remove     删除旧链接
skip       跳过
```

因此执行逻辑与展示逻辑是分开的：第 366 行之后才把这些记录渲染成普通文本，`--json` 则直接输出结果对象。

### 分别追踪三个目标

**Cursor：第 223–224、307–338 行**

目标路径是 `~/.cursor/plugins/local/csl`，来源是仓库根目录。

`ensureSymlink` 先解析真实来源路径，然后处理四种情况：

1. 目标不存在：创建链接；
2. 已经链接到同一来源：返回 `unchanged`；
3. 是指向其他位置的链接：删除后重建；
4. 是普通文件或目录：拒绝覆盖并抛错。

这里体现了安装器的重要原则：可以接管自己管理的链接，不能替用户覆盖未知实体。

**Codex：第 227–242 行**

实际顺序是：

```text
检查 codex 是否可用
→ 删除当前及旧版插件名称
→ 删除当前及旧版 marketplace 名称
→ 从 repoRoot 添加 marketplace
→ 安装 csl-agent-kit@csl-agent-market
→ 清理旧的 ~/.agents/skills 链接
```

命令数组的第三个值是 `allowFailure`。清理旧名称允许失败，两个新增操作不允许失败。新增失败会抛到 `installTargets`，成为该目标的失败结果。

旧链接清理由第 251–305 行负责。它只查看 `~/.agents/skills` 的直接子项，只处理符号链接，并确认链接来源位于当前仓库的 `skills` 目录中。

**Pi：第 244–249 行**

这是最短的一条路径：检查 `pi` 命令，然后同步执行 `pi install <repoRoot>`。

### 用一个调用检验你的理解

考虑：

```bash
csl-agent-kit install --yes --dry-run --verbose
```

逐步推导：

1. `parseInstallArgs` 得到 `yes: true`、`dryRun: true`、`verbose: true`。
2. 没有 `--all` 和显式 target，因此选择唯一默认项 `codex-plugin`。
3. 不进入交互，也不读取或保存历史选择。
4. dry-run 下不会执行 `codex --version`，八条 Codex 命令都变成计划记录。
5. 旧链接目录仍会被只读扫描，但不会 unlink。
6. 文本输出显示计划命令及可能计划删除的旧链接。
7. handler 没有抛错，因此进程按当前实现退出 `0`。

这个例子同时串起了默认选择、预览模式、命令建模和输出层。

### 三种错误出口

阅读时要区分：

- `die(...)`：参数、交互或确认错误，直接退出 `2`；
- target handler 抛错：由调度器捕获，最终退出 `1`；
- 缺失 `codex` 或 `pi`：返回 `skip`，但仍被调度器标成 `ok: true`，所以可能退出 `0`。

最后一种是代码语义中最值得记住的反直觉点：`ok` 当前表示“handler 没抛异常”，不一定表示“安装已经就绪”。

如果要继续自学，建议按这三个问题重新走读一次：

1. `--all --target bad-name` 最终会选什么？  
   答：全部目标，因为 `--all` 在 target 校验前返回。

2. 为什么 dry-run 仍可能读取用户目录？  
   答：它禁止写操作，但旧链接发现仍需读取目录和链接目标。

3. 新增一个 target 最少需要改哪里？  
   答：在 `targets` 添加一项并实现返回 change 记录的 handler；若 handler 有写操作，还要在真正副作用发生前遵守 `options.dryRun`。

按要求未改动文件，也没有运行组件、构建或测试。
