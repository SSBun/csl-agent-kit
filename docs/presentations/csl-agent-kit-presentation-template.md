## 1. 为什么设计它(Why,约 5 分钟)

**目的:** 讲清痛点 → 设计目标的因果链,不是罗列功能。

- **痛点(设计前的世界):**
  - 【占位:同一套工作习惯在 N 个宿主重复配置】
  - 【占位:规则随时间漂移,每个宿主的 Agent 行为逐渐不一致】
  - 【占位:好的 skill/流程锁死在单一宿主里,不可移植】
- **设计目标:**
  - 【占位:skills、rules、hooks、extensions 一次编写,多宿主分发复用】
  - 【占位:行为契约稳定——宿主可以换,工作流不换】
- **一个关键设计决策(观点示范):**
  - Skill 只是纯指令,宿主无关:所有具体能力(读写、搜索、shell、子代理)直接调用宿主既有机制,不在内部嵌套启动另一层 Agent CLI,也不写跨宿主适配层。指令直接依赖宿主现有能力,就永远不需要维护第二份"宿主行为事实来源"。

## 3. 为什么任务管理保持简单(核心,约 10 分钟)

**目的:** 用任务系统做样本,展示"克制"本身就是设计能力。这是全场核心论点。

### 3.1 先立骨架:任务文件是"结果契约",不是过程日志

- 【要点提示:先给听众三分工表,再引出下面的观点】

| 小节 | 职责 | 明确禁止 |
|---|---|---|
| Target | 可观察的过/败完成条件(唯一复选框列表) | 实现步骤、命令、评审状态 |
| Plan | 当前结果节点、依赖、下一步动作的薄快照 | 指定算法、文件、函数、调用路径 |
| Result | 每个 Target 一行证据 | — |

### 3.2 观点:强制"先弄懂再动手",但不强制"先写详细计划"

【成稿示例——可直接照讲】

所以设计上的强制项是:**Target 对齐 + 读完真实流程 + 记录当前路线**。缺的不是"详细计划",而是这个前置顺序——它已经强制了。

**为什么不该默认强制"详细实现计划":**

1. **计划比 diff 还长的任务,写计划就是浪费。** 一个根因明确的小修:先写一份 20 行的分步计划再改 3 行代码,是纯仪式(ponytail 原则:第一级阶梯是"这东西需要存在吗")。
2. **详细计划的主要价值(想清楚方案)在写薄 Plan 时已经兑现。** 真正防止改错的是"追踪完整流程后决定改哪里、为什么"——这落在 Plan 的当前路线和 Decisions 里。至于"第 3 步改第 42 行"级别的明细,写下来的那一刻就开始过时——过时的计划比没有计划更糟,因为它要么被盲从、要么被无视。
3. **强制产出会催生计划剧场。** Agent 会学会写"看起来详细"的计划来过关,而不是写"有决策含量"的计划。检查"是否先写了计划"是流程检查,不产生正确性。

**收束句(建议照讲):**

> 判定式只有三个问题:方案唯一吗?改错代价大吗?路径需要跨会话保留吗?三个都"否"→ 读完代码直接改;任一"是"→ 方案级计划进 Plan/Decisions;用户要明细 → 用专门的规划流程。强制点永远是"理解先于编辑",不是"文档先于编辑"。
