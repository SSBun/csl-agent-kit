## 对话

### User

How does it observe the session state and resume sessions?

### Agent

它通过“两套状态源”工作：

```text
Pi 实时生命周期事件 ──→ 判断 Session 是否存活、空闲、正在执行
工作区持久状态     ──→ 判断 Goal/List/Loop 应该恢复什么
```

## 1. 如何观察 Session 状态

插件订阅大量 Pi Extension 事件：

| 事件 | 用途 |
|---|---|
| `session_start` | 绑定新 Session、读取持久状态、决定是否恢复 |
| `session_shutdown` | 停止旧定时器、记录 handoff |
| `session_compact` | 标记压缩后需要重新同步和续跑 |
| `before_agent_start` | 确认自动发送的 continuation 真正启动 |
| `agent_start` / `turn_start` | 记录真实执行开始 |
| `message_update` | 记录模型仍在流式输出 |
| `agent_end` | 判断本轮结果，驱动下一轮 |
| `agent_settled` | Provider 重试完全结束后的恢复点 |
| `tool_call` / `tool_result` | 判断是否有真实工作和工具活动 |
| `model_select` | 记录模型切换、处理恢复策略 |

主要实现集中在 [`"/Users/caishilin/.pi/agent/npm/node_modules/pi-goal-list-loop-audit/extensions/loops/goal.ts"`](file:///Users/caishilin/.pi/agent/npm/node_modules/pi-goal-list-loop-audit/extensions/loops/goal.ts)。

它也会查询 `ExtensionContext`：

```text
ctx.isIdle()             Session 是否空闲
ctx.hasPendingMessages() 是否还有等待执行的消息
ctx.sessionManager       当前 Session 身份
ctx.cwd                  当前工作区
ctx.model                当前模型
ctx.getContextUsage()    上下文使用量
```

这些信息组合成 TUI 中的状态：

- `LIVE · WORKING`
- `BUSY`
- `QUEUED`
- `IDLE`
- `auditor running`
- `QUOTA WALL`

## 2. 如何识别主 Session

插件不会让任意 Session 都驱动工作。

它维护：

- 当前 `SessionManager` 对象身份
- Pi Session ID
- 工作区路径
- 插件实例 ID
- `sessionGeneration`
- 当前最新的 `ExtensionContext`

每次 Session 替换，`sessionGeneration` 都会改变。所有延迟回调、定时器和 Auditor 结果都会携带原 generation：

```text
callback.generation == current generation
                    │
           ┌────────┴────────┐
           │                 │
          是                 否
           │                 │
      允许继续执行       作为旧 Session 结果丢弃
```

Subagent 使用不同的 `SessionManager`，因此被识别为 foreign context：

- 可以执行普通工作
- 其工具活动可以计入活跃度
- 不能接管主 Session
- 不能驱动 Goal continuation
- 不能通过 glla 工具关闭主 Goal

## 3. 它持久化的不是 Pi 对话，而是“工作状态”

Goal 插件不会自己打开或恢复 Pi 的 JSONL 对话文件。Pi 负责 `/resume`、reload 和 session 切换。

插件恢复的是自己的工作平面：

- 当前 Goal
- 等待中的 List
- Loop 历史与最佳值
- Pending completion claim
- Provider 恢复状态
- 审计历史
- Continuation 状态

这些数据保存在当前工作区的 [`"/Users/caishilin/Desktop/personal/skills/.pi-glla"`](file:///Users/caishilin/Desktop/personal/skills/.pi-glla)。

核心状态账本是 [`"/Users/caishilin/Desktop/personal/skills/.pi-glla/active.jsonl"`](file:///Users/caishilin/Desktop/personal/skills/.pi-glla/active.jsonl)。

所以严格来说：

> Pi 恢复 Session；glla 在新的 Session Context 中恢复 Goal/List/Loop。

## 4. Session 关闭时做什么

收到 `session_shutdown` 后：

1. 记录 shutdown reason，例如 reload、resume、fork、new、quit。
2. 如果 Auditor 正在运行：
   - 停止旧 Worker
   - 保留 completion claim
   - 将状态改为 `recovery-pending`
3. 写入 session handoff。
4. 清除所有 Session 所属的：
   - continuation timer
   - loop timer
   - heartbeat
   - UI ticker
   - quota retry timer
5. 递增 generation，使旧回调全部失效。
6. 释放旧 `ExtensionContext`。

`quit` 被特殊处理：

- 用户退出不代表同意自动继续
- 不留下自动 handoff consent
- 下次启动默认只恢复状态，不自动执行

## 5. 新 Session 启动时如何恢复

收到 `session_start` 后，大致执行：

```text
取得新的 ExtensionContext
        ↓
验证它是主 Pi Session，不是 Subagent
        ↓
清除旧 stale 标记并增加 generation
        ↓
读取 active.jsonl
        ↓
恢复 Goal / List / Loop / Pending Audit
        ↓
检查是否存在两个活动对象并自动仲裁
        ↓
执行 Restore Gate
```

### Restore Gate 的默认策略

#### 默认冷启动

以下场景默认只加载，不自动执行：

- 启动新的 Pi 进程
- 用户通过 Pi `/resume` 打开一个会话
- `/new`
- 普通 startup

表现为：

```text
Goal  → paused，提示 /goal resume
List  → 等待，提示 /list next 或 /list resume
Loop  → held，提示 /loop resume
Audit → claim 保留，提示 /goal resume
```

这是为了避免用户一打开 Pi，旧任务立即开始消耗 Token。

#### 自动恢复场景

以下情况可以直接恢复：

- 同一进程的 reload
- fork/rebind 生命周期交接
- 有有效的 session handoff
- 全局 `autoResume = true`
- 用户显式执行 `/goal resume`、`/list resume` 或 `/loop resume`

`autoResume` 是全局设置，不接受项目级覆盖。

## 6. 恢复后如何重新驱动 Agent

Goal 恢复时不会简单发一句“继续”。

它会：

1. 检查 Session 空闲。
2. 检查没有 pending message。
3. 生成包含完整 Goal、验收合同和任务列表的 continuation prompt。
4. 在发送前写入 durable dispatch record。
5. 通过 `sendMessage(..., triggerTurn: true)` 发给 Pi。
6. 等待真实的 turn-start 证据。

Continuation 状态是：

```text
prepared → accepted → started
               │
               └─ 超时无启动证据 → unacknowledged
```

对应实现位于 [`"/Users/caishilin/.pi/agent/npm/node_modules/pi-goal-list-loop-audit/extensions/goal-loop-dispatch.ts"`](file:///Users/caishilin/.pi/agent/npm/node_modules/pi-goal-list-loop-audit/extensions/goal-loop-dispatch.ts)。

关键设计是：

> `sendMessage()` 成功只代表 Pi 接受了请求，不代表 Agent 真正开始执行。

插件必须看到匹配的 `before_agent_start` marker，或者兼容性的 `agent_start`、`turn_start` 等事件，才认定 continuation 已启动。

如果约 150 秒没有启动证据：

- 停止自动重发
- 保留工作状态
- 标记 interrupted
- 要求新 Session 或显式 resume

这样可以避免无效 Session 中的无限发送风暴。

## 7. 压缩后的恢复

Pi 上下文压缩触发 `session_compact` 时，插件会：

1. 标记 `postCompactResumeOwed`
2. 标记下一轮需要注入 resync 信息
3. 清除错误的 stall 计数
4. 给压缩过程一段宽限时间
5. 压缩结束后尝试重新发送 continuation
6. 若快速恢复失败，由 heartbeat 继续兜底

下一轮会收到类似：

```text
[POST-COMPACTION RESYNC]
对话刚刚被压缩。
以磁盘文件和持久 Goal 状态为准，
不要依赖压缩前的聊天记忆。
```

因为核心状态在工作区 JSONL 中，所以不会依赖 Pi 的模型生成摘要来恢复 Goal。

## 8. Auditor 如何跨 Session 恢复

如果 Session 在审计过程中被替换：

```text
auditing + running worker
          ↓ session shutdown
停止旧 worker
          ↓
pendingCompletion = recovery-pending
          ↓ fresh session_start
      ┌───────────────┴───────────────┐
有 auto-resume / handoff          没有恢复许可
      │                               │
直接重启 detached auditor          保持 paused
                                    /goal resume 后再审计
```

它重试的是原始 completion claim，不会重新要求执行 Agent 编造一次“我已经完成”的声明。

## 最重要的结论

它不是“恢复旧 Pi 进程”，而是：

```text
Pi 提供新的 Session Context
             +
glla 从工作区磁盘恢复 durable work state
             +
Restore Gate 判断是否获得继续执行的许可
             +
重新启动 continuation / loop / auditor
```

因此，同一工作区的多个 Session 共享同一份 glla 状态；session owner、generation 和 stale-context 检查负责确保旧 Session 不会继续驱动它。
