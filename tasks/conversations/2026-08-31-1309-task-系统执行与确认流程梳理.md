## 一、整体流程

```text
用户请求
   │
   ├─ 不触发 Task ───────────────→ 直接回答
   │
   └─ 触发 Task
        ↓
   创建/恢复任务 + task_focus
        ↓
   Task Target 对齐门
   ├─ L1 自动继续
   ├─ L2 确认一次
   ├─ L3 澄清一个问题
   └─ L4 批准目标变化
        ↓
   Context + Lessons + Authority
        ↓
   task / task-plan / task-queue
        ↓
   必要时单独进行 S1 Safety Confirmation
        ↓
   Result + Verification + 可选独立审查
        ↓
   complete → check → validate → 交付
```

### 1. 判断是否创建 Task

满足任一条件就进入 Task：

- 请求创建、修改、移动、重命名或删除文件，包括琐碎编辑。
- 请求形成一个具体、非平凡、可独立验收的结果。

简单事实回答、开放讨论和无文件变更的机械只读操作可以跳过。

**置信度：High**  
依据：[`"/Users/caishilin/Desktop/personal/skills/skills/meta/task/SKILL.md"`](file:///Users/caishilin/Desktop/personal/skills/skills/meta/task/SKILL.md) 第 26–33 行。

### 2. 激活任务

系统在实质工作前：

1. 查找是否已有对应任务。
2. 创建、恢复或重开 owning record。
3. 调用 `task_focus` 绑定当前会话。
4. 然后才进入 Target 对齐。

任务记录的创建只是生命周期操作，**不等于用户已授权执行**。

**置信度：High**  
依据：同一文件第 27、42 行。

### 3. 选择任务族

| 类型 | 用途 | 最终状态 |
|---|---|---|
| `task` | 实现一个可独立验收的结果 | 验证后完成 |
| `task-plan` | 调查并形成实施就绪交接，不修改交付物 | 保持 Pending，等待以后实施 |
| `task-queue` | 管理多个有序、可独立验收的子结果 | children 完成后再验证父级集成结果 |

## 二、确认节点

| 节点 | 触发条件 | 是否等待用户 | 含义 |
|---|---|---:|---|
| **L0** | 不需要 Task | 否 | 直接回答 |
| **L1** | 仅琐碎确定性文件编辑，且 Target 等价 | 否 | 自动继续；可不展示 Target |
| **L2** | 新的或实质修订后的非平凡 Target，与现有授权等价 | **是** | 核对 Agent 是否正确理解用户 |
| **L3** | 用户决策歧义导致无法形成诚实 Target | **是** | 只问一个聚焦问题；不是批准 |
| **L4** | Target 增加、遗漏、弱化或改变了承诺 | **是** | 展示差异并要求明确批准 |
| **S1** | 发布、安装、权限、破坏性操作等外部副作用 | **是** | 独立安全确认；不能由 L2/L4 代替 |

### 普通任务通常只有一次确认

典型非平凡任务是：

```text
创建并聚焦任务 → 展示 L2 Target → 用户确认一次 → 开始工作
```

以下情况**不会再次确认**：

- 同一 Target 已确认且没有变化。
- 只改变文件、函数、算法、命令或验证方法。
- Queue child 完全被已确认的 Parent Plan 覆盖。

以下情况会重新进入确认门：

- 用户修订结果或边界。
- Agent 或调查发现需要改变承诺。
- Queue 的 child 数量、顺序、结果或边界发生实质变化。
- 恢复会话后无法找回原确认依据。

**置信度：High**  
依据：共享协议第 64、193 行，以及 [`"/Users/caishilin/Desktop/personal/skills/skills/meta/task-queue/SKILL.md"`](file:///Users/caishilin/Desktop/personal/skills/skills/meta/task-queue/SKILL.md) 第 34 行。

## 三、`task-plan` 到实现阶段

正确流程是：

```text
task-plan 完成规划
    ↓
记录保持 Pending
    ↓
用户以后明确要求实施
    ↓
同一 record 交给 task
    ↓
重新应用 Target 对齐规则
```

这里**不要求额外询问一次“是否准备进入实现阶段”**。如果同一 Target 的接受证据仍可恢复且内容未变，可以直接继续；否则才展示 L2。

**置信度：Medium**  
“同一 record 交接”有直接规定；是否免除 L2 取决于当时能否恢复原确认状态。依据：`task-plan` 契约第 36 行和共享协议第 193 行。

## 四、Task 之外的条件确认

另外还有两个维护型确认，但它们不属于 L0–L4：

- Context 文件缺失时，创建前必须展示完整提案并确认。
- 持久新增、修改或删除 Lesson 前，必须展示精确内容或 diff 并确认。
