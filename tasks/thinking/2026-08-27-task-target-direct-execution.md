## 建议结论
建议把现行的“默认展示并等待确认”改为**双向语义等价门槛**：
> canonical task record 仍须创建或恢复并聚焦，Task Target 仍须形成。每当协议原本要求展示或重新展示 Target 时，先把候选 Target 与当前完整的用户授权承诺进行双向比较。实质等价则自动对齐；存在增加、删除、弱化或改变时，才展示并等待确认。
该门槛应同时适用于首次对齐、用户修订和 discovery realignment，而不能只修改 `Alignment Gate`。当前权威协议见 [`"/Users/caishilin/Desktop/personal/skills/skills/meta/csl-tasks/shared/protocols/task-target-alignment.md"`](file:///Users/caishilin/Desktop/personal/skills/skills/meta/csl-tasks/shared/protocols/task-target-alignment.md)。
### 审查发现
- **中等：**现行强制确认能防止 Agent 擅自决定结果与边界，但对已经完整授权的任务或修订仍会产生重复确认。
- **高：**宽泛的“明确任务可以直行”不足以阻止 Target 漏掉、弱化或改变用户已经提出的验收条件和保留边界。
- **高：**若只调整首次对齐，不同步处理 revision 与 realignment，协议会对相同语义采用不一致行为。
- **无阻塞项：**可以用窄而统一的语义规则解决，不需要风险评分、配置矩阵、新 UI 或持久 fast mode。
## 门槛真正防止什么
Task Target 确认不是让用户批准实现方法，而是防止 Agent 在用户尚未承诺时替用户决定：
- 最终结果；
- 怎样才算完成；
- 必须保留的行为或兼容性；
- 数据、范围或外部副作用；
- 用户拥有的实质性取舍。
当候选 Target 只是忠实表达用户已经授权的承诺时，重复展示没有增加安全信息。真正需要停顿的是候选 Target 与授权承诺不等价，包括过度承诺和欠约束。
## 比较基线：当前完整的用户授权承诺
比较基线不应只使用最初请求，而应包括：
- originating top-level request，但不把 `TASK_GO` marker 计入结果；
- 为形成 Target 而进行的聚焦澄清及用户答复；
- 用户明确提交的补充、删除、替换或修订；
- 用户对已展示 Target 的明确接受。
如前后表达冲突，以较新的明确用户表达为准。以下内容不能自行加入比较基线：
- Agent 的推测或偏好；
- 尚未获用户接受的 discovery 结果；
- Agent 自行选择的范围、兼容性或副作用；
- 仅因实现方便而产生的新约束。
`TASK_GO` 的位置检测保持现状：只检查 originating top-level request 的最后一个非空行。后续澄清或修订中的同名文本不应被当作该快捷授权。
## 双向语义等价检查
候选 Target 只有在以下方面均未增加、删除、弱化或改变时，才与当前授权承诺实质等价：
- Outcome；
- observable completion conditions；
- scope boundaries；
- preserved behavior；
- compatibility boundaries；
- side effects；
- user-owned trade-offs。
允许语言归纳、格式规范化，以及原请求必然蕴含的机械性验收表达；不允许用“概括”为名丢失用户约束。
建议使用对称的反事实测试：
> 如果用户可以合理地接受当前承诺却拒绝候选 Target，候选 Target 可能增加或改变了承诺。  
> 如果用户可以合理地接受候选 Target，但当前承诺仍可能未被满足，候选 Target可能删除、弱化或遗漏了承诺。  
> 任一情况成立，都不应自动对齐。
## 政策比较
| 政策 | 优点 | 问题 | 建议 |
|---|---|---|---|
| 始终确认，仅用 `TASK_GO` 绕过 | 确定性强，已有机制 | 用户必须预先知道 marker；明确请求和明确修订仍可能重复确认 | 保留兼容，但不作为唯一免确认路径 |
| “明确任务”自动免确认 | 表面简单 | “明确”主观，无法可靠防止过度承诺或欠约束 | 不采用 |
| 双向语义等价门槛 | 直接检查结果承诺是否改变，并能统一覆盖 initial、revision 和 realignment | 仍需有限语义判断 | **推荐** |
| 会话级或持久 fast mode | 可减少经常性提示 | 授权容易过期或跨任务泄漏，还会增加配置状态 | 暂不采用 |
## 首次对齐
owning record 激活且候选 Target ready 后：
- 若 originating top-level request 包含有效 `TASK_GO`，按现有语义处理；marker 仍不能消除歧义或批准实质不同的 Target。
- 没有 `TASK_GO` 时，将候选 Target 与当前完整的用户授权承诺比较。
- 双向实质等价时，自动视为已对齐并进入后续工作流。
- 不等价时，展示结构化 Task Target 并等待明确确认。
- 无法诚实形成 Target 时，只询问形成承诺所必需的用户拥有歧义。
自动对齐判断只能基于当前已授权对话内容，不能先调查、研究、规划或委派，再用所得信息证明无需确认。
## 用户修订与 realignment
### 用户明确提交的修订
当用户明确增加、删除、替换或改变当前承诺时：
- 先把该明确修订合入当前用户授权承诺；
- 再生成修订后的候选 Target；
- 候选 Target 与更新后的承诺双向等价时，直接更新 canonical Target 并继续，不再要求用户确认自己刚刚明确提交的内容；
- 用户修订不完整、有歧义，或候选 Target超出、遗漏、弱化该修订时，才澄清或重新展示。
因此，“用户的新请求实质修改当前承诺”本身不应无条件触发重复确认。关键在于修订是否由用户完整明确提交，以及候选 Target 是否忠实表达它。
### Agent 或 discovery 引入的变化
如果调查或执行发现需要改变结果、完成条件、范围、保留行为、兼容性、副作用或用户取舍：
- 该变化在用户接受前不是当前授权承诺的一部分；
- Agent 必须暂停并展示修订后的承诺，等待用户确认；
- 用户明确接受后，授权基线随之更新，不应再追加同义确认。
仅实现路径、函数、算法、内部计划或验证命令变化，而用户可见结果和边界不变时，不需要 realignment。
## 可以自动对齐的条件
以下条件均满足时，可以绕过对话式 Target 确认：
- owning canonical task record 已创建或恢复并聚焦；
- 当前完整授权承诺支持具体、可独立验收的结果；
- 候选 Target 与该承诺双向实质等价；
- 没有未解决的用户拥有歧义；
- 判断不依赖尚未获准开展的任务调查；
- 任何独立的安全、权限或发布门禁均未被当作 Target 确认一并绕过。
## 仍须确认或澄清的情况
出现以下情况时，应继续展示 Target 或提出聚焦澄清：
- 无法诚实写出可独立验收的结果；
- Agent 需要替用户在有意义的结果或取舍之间选择；
- 候选 Target 增加或改变原授权中的结果、范围、兼容性或副作用；
- 候选 Target 删除、弱化或遗漏完成条件、保留行为或边界；
- 删除、覆盖、发布、付费或外部通知的对象、范围或后果尚不明确；
- discovery 提出了用户尚未授权的实质变化；
- 用户修订本身不完整或存在多种合理解释。
## 安全边界
**Task Target 确认和安全确认必须分开。**
- Target 确认回答“承诺完成什么”。
- 安全确认回答“破坏性、不可逆或外部影响动作是否已获授权并允许执行”。
自动对齐不得绕过领域安全规则、权限检查、发布审批、数据保护或其他强制门禁。反过来，如果用户已经明确授权准确对象、范围和后果，也不应仅因风险较高就追加同义 Target 确认；领域规则要求的安全确认应独立执行。
如果 discovery 发现新的数据损失风险、外部接收方、不可逆后果或更大的影响范围，这属于 Agent 引入的新承诺，必须 realign，并在适用时另行取得安全授权。
## 最小可采用路径
不应只修改 `Alignment Gate`。应在权威协议中统一协调以下语义：
- `Alignment Gate`：首次候选 Target 等价时自动对齐；
- `Confirmation and Revision`：用户明确修订先更新授权基线，等价的修订 Target 不再重复展示；
- `Canonical Target and Realignment`：用户明确提交的等价修订可直接采用；Agent/discovery 引入的实质变化必须确认。
可采用的核心规则是：
> 每当协议准备展示或重新展示候选 Target 时，将其与当前完整的用户授权承诺进行双向语义比较。等价则视为已确认；不等价则展示并等待。用户明确提交的修订先更新授权基线；Agent 或 discovery 提出的变化只有在用户接受后才进入基线。
同时保持不变：
- canonical task workflow 的触发范围；
- canonical record 的创建、维护、聚焦和 Target 记录；
- 确认前禁止任务调查、规划、委派和交付物编辑的边界；
- `TASK_GO` 的精确位置检测和有限授权语义；
- Result、Verification、review gate 和完成门禁；
- 不新增持久 confirmation 字段、fast-mode 状态或宿主 UI。
## 代表性例子
**首次请求可自动对齐**
- “把设置页按钮改为指定文案，行为保持不变，并确认旧文案不再出现。”
候选 Target若完整保留文案结果、行为边界和验收条件，即可自动对齐。
**澄清后可自动对齐**
- 用户先说“改进 onboarding”。
- 聚焦澄清后，用户明确要求新用户能够完成账户连接并看到成功状态，同时保持现有账户流程不变。
后者已经成为当前授权承诺。候选 Target忠实表达这些条件时，不应再要求确认。
**用户明确修订可自动对齐**
- 用户在已形成的承诺上补充：“同时保持旧导出格式，并且不要上传云端。”
将这些约束加入授权基线后，等价的修订 Target可直接采用；若 Target漏掉旧格式兼容或云端边界，则不得自动对齐。
**Agent discovery 必须 realign**
- 用户只授权生成本地导出，但 Agent发现现有方案需要上传到外部服务。
外部上传不是用户授权承诺的一部分，必须展示新的副作用并等待接受。
**安全确认与 Target 确认分离**
- 用户明确要求永久删除指定备份，并明确知道不可恢复。
同义 Target可自动对齐，但适用的删除安全规则仍须独立执行。
## 跨主题影响与不确定性
这项政策减少的是重复的对话确认，不取消任务追踪，也不降低交付门禁。canonical Target 仍是持久承诺记录；自动对齐只改变是否等待额外文本确认。
目前没有实证 UX 数据可量化摩擦改善或误判率。主要残余风险包括：
- Agent 对实质等价的判断可能不一致；
- 欠约束比过度承诺更难被察觉；
- 若只修改部分协议条款，会形成 initial、revision 与 realignment 行为冲突。
推荐默认值是：
- 双向等价时自动对齐；
- 有合理可能增加、删除、弱化或改变用户承诺时确认；
- 用户完整明确提交的修订不重复确认；
- Agent/discovery 引入的新承诺在获用户接受前不得直行；
- 可逆且不改变用户承诺的实现选择采用合理默认；
- 暂不引入会话级或持久 fast mode。
