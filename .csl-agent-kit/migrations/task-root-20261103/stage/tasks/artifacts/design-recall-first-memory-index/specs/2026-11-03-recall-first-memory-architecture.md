# 召回优先的 Memory 架构设计

版本：设计稿 v1；日期：2026-11-03。

状态：供后续实施的架构提案，不表示运行时已实现，也不替代现有正式规范。用户已认可召回优先、多入口和检索卡片方向，并明确要求本文；具体schema、预算、迁移步骤与验收阈值属于本提案。实施须另行对齐，不自动改写既有Topic规格。

## 1. 目标与边界

最重要的目标是：在有限上下文中，可靠找回当前任务所需的有效知识，包括适用条件、例外和纠正关系。先保证召回及使用正确，再优化token和延迟。

不把以下指标当成目标本身：索引越短越好、读取次数越少越好、记忆数量越多越好、全部文件读过就算理解、每次加载全部正文。

保留现有约束：

- Markdown是权威；user/project独立作用域，读者用普通read/grep/find，不依赖后台在线、专用检索API、数据库或向量服务。
- 主题由实际内容形成，不预设领域分类或Core/Normal层次；type仅作描述，不作为硬过滤器。
- 两级记忆由后台Memory Agent自主维护，保留来源、适用范围、revision/hash条件写入、锁、审计和恢复。
- 前台Agent负责检索和完成任务，不承担例行记忆整理；前台退出不终止持久队列的处理。
- 不因近期没有使用而删除知识，不以预算截断有效内容；不把语义判断伪装成程序可证明的事实。

本轮只有设计文档，不修改产品或真实记忆，不执行新的模型实验。

## 2. 当前实现与证据

当前条目是带YAML头的Markdown，索引行包含title、summary、type、revision和完整文件hash。store.indexPages按字符预算切成首页与不可变代际续页；Pi在before_agent_start注入两级首页，后续由Agent决定翻页或搜索。写入经过pending日志、正文替换、索引发布、审计完成与恢复流程。

2026-11-03先导实验执行36次请求，两组各18/18成功。分页组总token为295,904，完整索引组为1,138,743；耗时中位数分别为13.58秒和11.08秒。50文件时完整索引token略少，200/1000文件时分页更少。两组实际均先read索引；未测试明确的search-first策略、生产首页注入或困难无关键词语义召回。

因此，现有证据支持“首次read大小会影响本次工作负载成本”，不支持“分页已保证高召回”，也不支持“完整索引或层级索引一定更好”。本设计是需要验证的替代候选。

当前分页主要解决一次读多少，不能回答相关知识在哪里。直接换成树也不能解决全部问题：分类错误、跨主题知识和不匹配的提问措辞仍可能漏检。

## 3. 核心对象与单一权威

### 3.1 Memory chip：连贯知识单元

chip沿用现有entry身份和正文，不另起一套知识存储。它不是单个事实的一行记录，而是可以独立正确使用的知识单元；结论、必要条件、例外、来源应就近保存。没有理由为了“chips很多”拆散相互依赖的知识。

身份使用(scope, id)。同名或相同id在两级之间不自动视为同一条；不把项目知识复制或提升为用户知识。项目规则只在证据明确时覆盖用户默认，并且不改变用户原记录的有效性。

### 3.2 检索卡片：可重建发现入口

每个非墓碑chip必须有且仅有一张规范卡片。卡片包含标题、覆盖摘要、别名/相关说法、适用情境、正文链接、关联提示以及来源revision/hash。

卡片不是第二份权威知识。它是条目元数据的确定性投影：用于选候选，不能替代正文或授权动作。修改卡片必须回到对应chip的受控写入；不允许后台Agent直接编辑派生卡片。

### 3.3 主题索引：多入口导航

一个chip可归入多个动态主题；每个主题索引列出该主题相关卡片的短描述和链接，所有入口最终指向同一正文。主题不完整或分类暂时不准确，不能影响卡片库的完整覆盖。

### 3.4 薄总览：范围提示，不是检索全集

首页展示作用域、generation、有效chip/卡片数量、索引健康状态、全卡片库入口及主题导航入口。它只提供路标，不承诺列出所有chip，也不能成为排除其他知识的依据。

## 4. 逻辑存储布局

以下为相对于每个Memory根的拟议布局，不是本轮新增的实际运行目录：

```text
entries/<id>.md                    权威chip，沿用身份
index.md                           当前薄总览与代际入口
.indexes/<generation>/
  manifest.json                    确定性生成的身份/完整性清单
  cards/<id>.md                    完整、可搜索卡片库
  topics/<topic-id>.md              主题及子主题导航
  topics.md                        全主题目录；按需搜索/分段读
.history/                          沿用审计
.pending.json                      沿用并扩展恢复契约
.format.json                       数据与读写兼容版本
.migrations/                       升级备份与进度
.service/                          仅用户根，沿用后台队列与状态
```

index.md必须明确提供本代cards目录的实际路径。普通grep/find工具常默认忽略隐藏目录，不能让Agent从Memory根盲搜“.indexes”，更不能搜索全部历史代际。读者必须搜索首页声明的当前cards目录；历史目录、审计、备份和待批提案不是有效知识源。

manifest.json仅做机械对账，正文仍为Markdown；无需读者先解析整份JSON。正常检索不加载整个卡片库。旧代只作短期读者一致性和恢复用途，不能混入当前全库搜索。

两级根分别发布generation，不承诺跨user/project原子快照。检索记录两者的代际，遇到跨级变化按相关范围重查。

## 5. 拟议数据契约

### 5.1 条目升级

现有csl-memory/v1解析器严格拒绝未知字段，不能直接悄悄添加属性。本提案使用新entry schema csl-memory/v2，保留id、revision、title、summary、type、sources、updated、deleted及正文，新增可选retrieval字段：

| 字段 | 含义 | 边界 |
| --- | --- | --- |
| aliases | 术语、缩写、同义或常见表达 | 有正文依据，不能堆砌无关热词 |
| situations | 什么任务、问题或条件下可能需要该chip | 是发现线索，不代表已经满足执行条件 |
| topics | 一个或多个动态主题路径，如主题/子主题 | 语义标签而非文件路径，无预设清单 |
| links | 关联chip引用及关系类别 | 引用(scope,id)，不接受任意文件路径 |

summary作为覆盖摘要，不另设重复的coverage字段。正文仍负责完整资格条件；卡片必须提示重要限制存在，而不是试图容纳全部细节。没有额外别名或情境时允许字段为空，不能为满足模板制造信息。

最小links类别：related（建议扩展）、requires（使用结论前需核对）、supersedes（完整替代旧chip）。supersedes只允许同一作用域，且必须有完整替代的证据；部分纠正优先在原chip内更新，不能用整体替代关系隐藏仍有效的其他段落。跨作用域覆盖用正文限定和related表示，不把用户默认作废。

关系不是自动采信命令。编译器检查目标格式、可用目标、重复、自引用及supersedes环；语义是否真的替代由Agent结合来源判断。跨级requires仅解析当前workspace与用户根，不允许借引用读取其他项目。不可访问的必须依赖不能静默省略。

### 5.2 卡片投影

卡片的全部可搜索语义来自同一revision的title、summary、retrieval及明确关系；正文hash由writer根据完整字节计算，不能写入被hash的chip自身。

卡片包含：scope、id、entrySchema、revision、sourceHash、正文相对链接、上述检索字段、派生的被替代提示，并绑定所属generation。topics和supersedes的反向入口由编译器确定性计算，不要求模型同时修改两份记录。因此sourceHash只证明正文身份，generation还承担派生关系的版本身份；旧正文未改变不代表旧卡片的反向关系仍然有效。

完整卡片库也覆盖未分类及尚未语义增强的旧chip。缺少retrieval时直接从现有title/summary生成基础卡片，并标明检索线索尚未增强；不等待LLM整理后才允许读取。

### 5.3 主题生成

Memory Agent在更新chip时声明动态topics，编译器按这些标签生成目录和成员链接。标签规范化只处理明确的空白和Unicode规范形式，不自动把语义相近词合并。topic-id从规范化标签生成并检查碰撞，不把模型输出直接拼成磁盘路径。

主题路径可表达父子结构，同一个chip可以同时出现在多个分支。主题导航的覆盖描述来自子主题标签和成员短描述，不另维护一份无来源的自由摘要。需要主题合并、拆分或改善名称时，由Agent以条件写入更新相关chip的标签；中间状态允许多入口并存，卡片覆盖不受影响。

主题大到难以浏览时优先做语义拆分。工具输出仍可能需要分段/分页读取，但不把无语义的页号当主要导航架构。

## 6. 召回协议：导航和搜索互补

前台使用agent-memory中的读取规范执行下列协议；后台维护调度和知识提取仍不写入该Skill。现有dashboard管理入口保留。

### 6.1 建立检索需求

先把当前任务拆成少量“需要知道的事项”：涉及对象、动作、适用范围、约束、可能的例外。它们是本轮检索计划，不是持久分类模板，也不需要新增数据库。

每个实际允许的作用域都应进入发现阶段。不能因为当前在项目中就默认跳过用户级，也不能因为某条属于experience就排除它。

### 6.2 同时使用两条发现路径

1. 读两级薄总览，固定本轮generation与cards路径。
2. 根据相关主题查看候选卡片。
3. 针对需要知道的事项，在两级完整卡片库搜索对象名、动作、术语和合理改写。主题导航命中不能替代全库搜索；两路“同时”指都要覆盖，不要求工具并发。
4. 候选按(scope,id)合并去重，不能只保留第一个主题的结果。

卡片库是完整收录的检索面，不意味着任何关键词查询都能命中所有语义相关知识。

### 6.3 阅读与扩展

- 对将用于决策的候选读取正文，确认来源、条件、例外与版本；卡片摘要不直接作为执行依据。
- 顺着requires读取必要依赖，检查supersedes的替代者；related作为扩展线索，不递归加载全部关系图。维护已访问集合，检测循环。
- 检索未命中、只有弱相关结果、发现条件缺失或相互冲突时，扩展措辞和关联主题，并在权威entries中搜索正文。
- 正文搜索可能命中墓碑或被完整替代的旧chip；先验证生命周期和替代关系，再决定是否适用。墓碑只作状态线索，不引用其删除说明作知识。
- 关键词仍无法表达问题时，可分批检查相关范围的卡片摘要；没有明确范围时允许扩展至全卡片库。不得把固定top-k候选当作完整集合，也不得凭“已搜索三次”宣布不存在。

### 6.4 覆盖检查与停止

在会话内维护简短覆盖表：需要知道的事项、已核对chip、关键条件、尚缺证据。此表不是新的长期记忆或任务进度存储。

正常停止需要：当前任务的必要事项已有正文支持；重要requires与替代关系已核对；无未处理的关键冲突；相关搜索结果未因工具截断而遗失；对会改变结论的限定条件已检查。无论是采信已找到的结论，还是报告未找到知识，都必须先执行第7.3节的相关作用域pending/generation复查；发生变化时刷新候选与关系，不能仅凭正文hash不变通过。高后果事项同时查当前权威来源，记忆不能自行成为批准证据。

资源不足时可以停止，但结果必须标为“检索未完成/覆盖有限”，说明缺失范围；不声称“系统没有此知识”。即使完成预定搜索，也使用“在已检查范围内未找到”，不承诺任意语义上的绝对不存在。

该协议降低可避免遗漏，不是零遗漏证明。完全零遗漏既不能由有限关键词搜索保证，也不能由“读了所有文件”保证。

## 7. 完整性与发布一致性

### 7.1 程序能够保证的部分

在受控写入范围内，每个已发布generation必须满足：

- 每个非墓碑chip都有一张卡片，卡片集合与有效chip集合精确对应；被完整替代但尚未墓碑化的chip仍有带替代提示的卡片，不静默隐藏。
- 卡片的revision/sourceHash对应构建时实际正文；每个正文链接和主题成员链接解析到允许范围。
- 每个有效chip即使无topics也在完整卡片库；任何主题分支均不成为排除性权限边界。
- 代际清单涵盖entry身份、卡片身份、主题文件及schema，数据格式验证失败则不发布半成品。

无法通过计数证明别名充分、摘要保留全部重要条件或查询改写正确。这些由语义维护与带gold的召回评测检验。

### 7.2 沿用受控事务并扩展派生构建

1. 在当前作用域write lock内核对expected revision/hash，校验新schema和关系。
2. 持久化审计准备记录及pending，再原子替换chip正文。
3. 从此时有效条目集合确定性生成新代的卡片、主题、manifest；全过程不调用LLM。
4. 验证集合完整性与链接，最后原子替换index.md，发布完整新代。
5. 完成审计并清理pending；返回提交身份。

没有新增跨文件原子事务承诺。沿用RECOVERY_REQUIRED语义：失败可能发生在正文已替换后，必须按beforeHash/afterHash恢复，不自动重放语义写入。恢复器将“重建索引”扩展为重建完整卡片/主题代际；重建失败仍保留pending并报告异常。

首次实现优先全量确定性重建，复用现有模式，不提前引入增量索引服务。其O(n)成本需要在正式工作负载中测量；若确有瓶颈，再设计增量构建但不得削弱发布校验。模型生成的语义线索在提交前准备，不能让锁等待模型。

### 7.3 无锁读取与陈旧检测

读者可固定一个完整代际用于导航，但正文不是该代际的不可变副本。读正文时核对卡片revision及重要决策所需的完整文件hash；发现不匹配，重新读取当前首页与相关卡片，必要时退回正文搜索。正文身份与派生关系身份必须分别校验。

在采信任何候选结论或报告未找到知识之前，对所有参与发现及依赖核对的作用域重新读取首页generation、检查pending，再复读generation。观察到pending、代际变化、卡片缺失或链接损坏即不能以旧导航通过覆盖检查。已发布新代时，切换到新代并刷新候选卡片、反向supersedes及requires，读取新增替代者/依赖，重新判断相关条件；不能因旧正文revision/hash不变跳过此步骤。仍有pending或新代不可用时，标记索引降级并搜索当前entries中的正文与关系元数据，不等待后台；若无法核实是否已被替代，则把该结论标记为未确认，不继续采信旧结论。

例如读者在G1找到A后，writer新增B并声明B supersedes A，发布G2而不修改A。正文校验A仍可通过，但采信前代际复查会发现G2，必须读取新卡片和B，不能继续使用G1中缺少替代提示的A。该规则同样适用于已经命中的知识，不只是查询无结果。

user/project分别校验；跨级读取不构造虚假的全局一致版本。上述无锁检查只约束最后观察到的代际，不保证最后一次检查之后不会有新写入，也不承诺检索与后续外部动作构成原子事务。高后果动作仍需执行时的权威校验；连续变化或关系核对不完整时披露覆盖限制，不无限重试。直接绕过writer改正文不在受控保证内，reindex/完整性检查应报告漂移，不能声称普通文件读取可防住所有外部篡改。

旧代暂不自动垃圾回收，避免仍持有旧链接的读者被打断。沿用当前保留策略并报告磁盘增长，不以近期未访问为理由删除知识；代际清理若另行实现，只清理可重建派生数据并明确读者生命周期。

## 8. 简洁读取与预算

简洁来自分工，不来自减少必要知识：启动只给总览，搜索只返回候选，正文按需读取，但必要条件必须完整检查。

| 对象 | 拟议策略 | 超限行为 |
| --- | --- | --- |
| chip正文 | 沿用当前4000字符目标、普通写入8000字符边界，历史保真例外不变 | 按连贯知识拆分，先保存并核验，再移除旧内容 |
| 单张卡片 | 200—600字符作为初始观察目标，不作为信息截断上限 | 检查冗词与chip粒度；关键条件的发现线索不得静默删掉 |
| 薄总览 | 沿用现有4000字符注入预算 | 退化为统计、健康状态、完整卡片路径和主题目录入口；不假装展示全部主题 |
| 主题索引 | 保留全部成员；大主题按语义拆分 | 工具分段读取需明确续读；未分类chip仍在卡片库 |
| 全卡片库 | 不限制总卡片数或总知识量 | 普通搜索和按需读取，不全文注入 |

新增卡片目标未经实验验证，不能作为性能承诺。工具自身的行数/字节截断必须可见；缩小查询、读取后续范围或换检索方式后才能认为候选处理完整。不能把文件大小估算冒充模型token测量。

## 9. 语义维护与质量反馈

后台Memory Agent沿用每workspace隔离复用会话与持久队列。处理可见对话增量时，先读现有chip，再决定更新正文及检索线索；一次受控修改同时保存两者，避免模型分别维护卡片和正文。

每次新增/实质更新须检查：从常见任务表述能否找到、摘要是否提示重要条件、别名是否有依据、requires/替代关系是否正确。它是语义检查要求，不是程序已经证明的覆盖率。

主题整理只改检索元数据，不自行改变知识权限或来源。新增主题不需要用户选择固定模板；同一主题的表达合并必须保留原发现入口或别名，不能为了目录整齐损害召回。

前台若实际发现遗漏或误用，把事实及证据留在正常任务记录/可见回复中，后台消费现有增量再处理；不新增前台强制提取流程，不把模型生成的“检索没发现”自动当作删除证据。

不引入未经授权的全库定时模型扫描、自动实验或大规模查询扩写。是否需要这些能力，须由后续真实质量数据支持。

## 10. 故障与降级

| 情况 | 行为 | 禁止行为 |
| --- | --- | --- |
| 无主题或主题错分 | 搜索完整卡片库，必要时正文兜底 | 因导航没列出而视为不存在 |
| 卡片尚未语义增强 | 使用基础title/summary卡片并允许正文搜索 | 等待LLM完成才让chip可见 |
| 卡片/主题代际构建失败 | 保留旧完整代和pending，当前读取显示降级，恢复后重建 | 发布部分卡片或虚报全库覆盖 |
| 版本/hash不匹配 | 重新核对当前正文与相关关系 | 使用旧摘要直接决定 |
| 必须依赖丢失/不可读 | 标记该结论证据不完整 | 默默省略依赖后继续采信 |
| 发现矛盾或部分纠正 | 读来源与范围，未解决则披露 | 仅凭更新时间、热度或主题位置选赢家 |
| 服务或模型不可用 | 普通工具读取现有Markdown，维护事件按现有协议保留 | 阻塞所有读取或伪称已整理 |
| 搜索输出截断或预算耗尽 | 扩展/续读或报告覆盖有限 | 把工具第一页当完整结果 |
| 主题/别名带指令文本 | 当作不可信检索资料，核对正文与权威规则 | 扩权、执行shell或改变用户授权 |

卡片与主题导航同样可能含私密信息；它们不应跨作用域复制用户资料，也不应进入公共日志。现有loopback面板鉴权和不记录访问令牌的边界不变。

## 11. 从现有实现演进

### 11.1 组件职责变化

| 组件 | 保留 | 拟议变化 |
| --- | --- | --- |
| store | Markdown、CAS、锁、审计、墓碑、恢复 | 新schema与retrieval验证、卡片/主题编译、完整性校验和发布 |
| migration | 自动版本检查、备份、幂等、保真 | 新增当前store v2到新store版本的明确转换路径，不重导旧Context/Lessons |
| Memory Agent | workspace会话、独立模型、受控写入 | 学习维护发现线索、动态主题和关系；不直接编辑派生文件 |
| Pi bridge | 增量持久化、后台不阻塞主任务 | 注入薄总览及当前cards位置、索引降级状态，改用新检索协议 |
| 启动hook | 两级初始化与故障披露 | 与Pi共用新版本/总览读取契约，避免保留另一套旧索引加载逻辑 |
| CLI/Web | 现有dashboard入口、审计恢复与模型配置 | 显示chip/card覆盖数、待增强数、代际状态、损坏引用与最近重建错误 |
| agent-memory Skill | 通用读写规范及dashboard入口 | 更新卡片发现、正文核对、覆盖检查与降级规范；不放调度和提取流程 |

### 11.2 升级与回退

当前store格式version=2、entry schema=v1、index schema=v2三者是不同版本维度。本提案升级store版本以表示新写入契约，entry使用v2，派生index/card/topic使用各自新schema；具体常量统一由实现定义。未知未来版本失败关闭，不猜测兼容。

1. 在升级前保存当前条目、格式标记、当前首页及必要代际清单，并记录完整hash；不移动或删除旧源。
2. 迁移器暂时读取v1/v2，逐条通过可恢复、可审计路径转换。id不变，revision增加，正文、来源和已有有效修改逐字保留；retrieval可为空。墓碑保留，不重新创建为有效chip。
3. 格式未完成时，新reader允许读取已转换和未转换条目并明确状态；新writer先完成当前作用域升级，再接受普通变更。不能在半升级状态使用旧writer写新schema。
4. 构建所有基础卡片与主题入口，检查覆盖和hash后再切换首页及完成格式标记；升级不依赖模型，不要求用户逐条批准。
5. 重启后根据已完成条目、审计和当前hash续做，不重新导入旧Context/Lessons，不覆盖升级后已发生的新修改。`upgrade --dry-run`列出影响与备份位置。
6. 后台之后再逐步增强aliases/situations/topics；基础卡片已经可读，不以增强进度阻塞知识可见性。

迁移期间旧进程不能继续写。升级入口必须先识别不兼容服务/客户端并拒绝并发写，必要时要求显式重启；不能仅靠新reader承诺而让旧进程破坏新schema。这是实施前必须验证的升级门禁。

回退不是把旧快照覆盖到当前目录：有升级后写入时必须先导出/对账保存新增知识。可回退到兼容新格式的前一运行版本，或在没有后续写入且完整校验通过时恢复全套升级前备份。旧二进制直接写新store不受支持。迁移完成后不保留长期双写权威。

## 12. 召回优先验收

### 12.1 结构验收

- 非墓碑chip与卡片集合精确对应；未分类和待增强记录也覆盖。
- 引用安全、成员链接可解析、requires/替代环有确定处理；关系反向入口与原关系一致。
- 模拟正文已替换但卡片未发布、发布中断、旧代读取、两级独立变化和外部漂移，不能出现静默假完整。
- 必须覆盖“读者G1命中A；仅新增B supersedes A并发布G2；A的正文/revision/hash不变”的时序：采信前必须发现代际变化、刷新反向关系并核对B。还须覆盖关系构建仍pending时拒绝把A当作已确认结论，以及连续变化时明确降级而非无限重查。
- v1历史条目、超预算保真资料、墓碑及升级后新写入均不因迁移丢失或重复导入。
- 不引入专用读取服务；模型/后台关闭时仍可用普通工具检索。

### 12.2 行为验收

gold以当前任务所需事实和资格条件为单位，不以读过的文件数或token少作为成功标准。增加无精确对象词、跨主题、多文件依赖、主题错分、例外仅在正文、同名不同作用域、部分纠正、完整替代、无答案及截断续读问题。

主要指标：必要事实召回率、关键条件/例外遗漏率、范围/版本误用率、正确拒答及严格任务成功率。记录找到卡片但未读取必要正文、已读但没用于答案、因主题/关键词/截断漏检等不同失败原因。成本和耗时只在质量约束下比较。

对照至少保留当前分页和完整索引两种基线，新增本设计；另外把search-first指令与索引结构作为独立因素，避免把提示改进全部归因于架构。配对相同信息和工具，问题集与容忍阈值在运行前冻结，重复和规模不冒充独立题目。

最低实施门槛是结构覆盖完整、关键范围误用与条件遗漏的冻结必过案例零失败；这只证明测试案例通过，不等于真实世界零遗漏。总体质量是否改善必须有足够困难题与配对区间支持。沿用“质量优先于成本”的顺序，但不沿用先导试跑全成功就判非劣的错误推论。

具体样本数、允许的质量差值和成本预算在新的实验执行前确认；本稿不自动授权原计划432次或任何新批次。未取得质量证据之前不替换正式检索策略。

## 13. 实施顺序与待验证假设

建议顺序：数据契约和兼容读写门禁 → 基础卡片编译及恢复 → 薄总览和普通工具检索 → 主题多入口与语义增强 → 故障和召回评测 → 根据证据决定生产切换。

这是依赖顺序，不是自动执行的任务队列。首版不新增向量库、排序模型、自动删知识、跨项目共享库或长期维护评分服务。

待验证：

- 多入口与情境线索能否真正改善无精确词召回，而不是只增大卡片。
- 全库卡片搜索加导航是否比正文直接搜索产生更少遗漏。
- 强制先搜索的提示与索引结构各贡献多少收益。
- 主题维护成本和全量代际重建在真实规模下是否可接受。
- 现有工具对隐藏代际、结果截断和相对链接的处理是否需要最小适配。

任一假设不成立都应调整设计，不能以已经写出文档作为架构正确的证据。
