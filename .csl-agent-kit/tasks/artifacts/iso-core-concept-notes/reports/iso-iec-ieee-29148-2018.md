# ISO/IEC/IEEE 29148:2018：需求工程核心概念

## 标准身份与阅读边界

- 英文名称：Systems and software engineering — Life cycle processes — Requirements engineering。
- 版次：2018年，第2版。
- 本文基于ISO、IEEE和IEC公开介绍作中文概念提炼，未逐条核对付费标准全文，不提供条款级合规结论。
- 以下“核心概念”为解释性归纳；“Memory应用”与例子是本地建议，不是标准规定的模板。

## 核心概念

### 1. 需求工程覆盖整个生命周期

需求工程包括识别需求、分析和表达需求、核对需求，以及管理需求的变化。它适用于系统、软件产品及相关服务，不只发生在开发开始前。

需求会随着对问题的理解而细化。细化时需要维护上下层要求之间的联系，避免某个实现选择改变原始目标却没有被发现。

### 2. 区分目标、需要和可检查的要求

利益相关者提出的愿望，需要转换成能够指导设计和验收的要求。例如，“让恢复更可靠”表达目标；“检测到配置不完整时停止启动并返回明确错误”表达一个可观察要求。

转换不能凭空增加义务。需要明确哪些来自用户或其他权威约束，哪些只是实现方案。

### 3. 单条需求应有清楚的含义

良好需求表达应减少歧义，明确对象、条件和要求的结果。一个句子同时混入多个独立要求，会增加验证和变更的难度。

必要的阈值、单位、否定及例外属于需求含义。删去它们可能使文字更短，却改变实际要求。没有必要时，不把需求限定为某个具体实现方法。

### 4. 一组需求也需要整体检查

单条语句清楚，不代表需求集合完整。还需要检查遗漏、相互矛盾、重复、不可实现的组合，以及上下层要求是否一致。

例如，一项要求规定“所有错误必须停止处理”，另一项要求规定“任何情况下都继续处理”，即使分别写得清楚，也仍然冲突。

### 5. 区分验证与确认

可以从两个角度检查需求：表达和技术条件是否足够明确、完整、可检查；这些要求是否确实回应利益相关者的需要和使用情境。

“实现满足了写下来的条件”和“写下来的条件就是正确目标”是两个不同问题。本文使用这一通用区分帮助阅读，不据此替代标准中的完整过程定义。

### 6. 需求信息和变更需要管理

标准不仅关注句子，还涉及需求工程过程产出的信息项、内容及格式指导。需要保留适当联系，使后续人员能理解要求的来源、依赖和变更影响。

这些联系可以由正式需求或Task系统管理，不意味着每份摘要都必须复制完整追踪数据。

## Memory应用：本地建议

- 对约束案例，写清“在什么条件下，哪个对象需要满足什么结果”。
- 对经验案例，保留触发条件、防护动作和可观察检查。
- 对事实案例，保持描述，不强制改写成要求。
- 保存前检查案例之间是否冲突，尤其是范围相同但行为不同的要求。
- 要求强度另按RFC 2119 / RFC 8174表达；29148并不等同于关键词检查。
- 正式需求变更和验收证据留在Task或需求系统中；Memory只保留复用时必要的知识。

## 示例：从模糊建议到可用经验

较差：

> 修改格式后做好验证。

改进：

> 修改共享数据格式后，同时检查写入方和读取方使用的字段定义。仅通过写入校验，不能证明读取兼容。

改进后的句子给出触发条件、检查对象和证据边界。若要将其标为强制要求，还需要已有权威规则支持，不能仅因措辞更明确就增加MUST。

## 常见误用

- 把实现偏好包装成用户要求。
- 认为出现MUST就证明要求清楚且可验证。
- 只检查单句，忽略要求之间的冲突。
- 为追求形式完整而编造阈值、责任人或验收指标。
- 把需求工程标准当作Memory文件格式标准。
